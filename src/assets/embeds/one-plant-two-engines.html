One Plant, Two Engines

The robot's plant model is written twice, once for the CPU oracle and once for the GPU trainer. This page explains why that happened, what it costs, what other robotics projects do about the same problem, and a plan to write it once.

1 The problem

You change the reward in one file and forget the other. The GPU trains for six hours on the new reward. The CPU oracle still scores the old one. Every evaluation you run afterwards compares two different tasks and nothing tells you.

That is not hypothetical. The repository has eight pieces of plant logic that exist twice: once as plain numpy for one robot, once as torch for a thousand robots at a time. The two copies are kept equal by a set of parity tests, which means every change is two edits and one test run, forever.

2 What is really duplicated

It is tempting to describe this as "numpy versus torch" or "PyBullet versus MuJoCo". Neither is the real split. Three facts from the code show that:

  • The numpy models already run against MuJoCo. The single-robot MuJoCo backend in wlbot_mjlab/sim/mujoco_backend.py imports the numpy motor, battery, servo and push models. Engine-agnostic is already true.
  • Every constant is already shared. The torch copies import the reward weights, the observation names and scales, the estimator constants and the action scale from wlbot. Only the step-by-step math is written twice.
  • The torch copies are already written in the style the unified code needs. They keep a boolean mask per robot instead of an if, and they can reset a subset of robots. That style runs unchanged with one robot.

So the real axis is one robot at a time versus a thousand at once. The numpy code holds one number per quantity and branches with if. The torch code holds a column of numbers, one per robot, and branches with a mask. The engines are innocent bystanders. What wlbot is missing is not engine independence, it is a batch dimension.

The same step, in both styles

One tick of the firmware pitch estimator. The accelerometer correction only applies when the reading is trustworthy.

One robot, today

pitch += gyro * dt
if acc_ok:
    pitch += (dt / (tau + dt)) * (acc_angle - pitch)
else:
    rejected += 1

Any number of robots, proposed

pitch = pitch + gyro * dt
pull  = (dt / (tau + dt)) * (acc_angle - pitch)
pitch = torch.where(acc_ok, pitch + pull, pitch)
rejected = rejected + (~acc_ok)

On the right, acc_ok is a column of true and false values, one per robot, and where picks per robot. With one robot the column has one entry and the code does exactly what the left does. That is the whole trick, and it is why one implementation can serve both.

3 Two ways to write it once

Both options keep one copy of every model in wlbot, written in the batched style above. They differ in which array library runs it on the CPU.

A One source, two array libraries

Each model takes an array module as a parameter. On the CPU it is numpy, on the GPU it is torch. numpy 2 adopted the Python array API standard, so most function names now match torch, and the idea is that the same source runs under either. SciPy and scikit-learn use this pattern for library code that has to accept whatever arrays a user hands them.

B One source, torch everywhere

Each model is a torch class with state shaped [n, …] and a device argument. The CPU oracle runs it with n = 1 on the CPU device. The GPU trainer runs it with n = 1024 on CUDA. This is how NVIDIA Isaac Lab and mjlab write their actuator and noise models, and both unit-test those classes at one environment on the CPU alongside CUDA.

Scored on the thing you actually fear

The question is not which is faster or lighter. It is how many places the same law can be written differently.

The second row is the important one. Under A the code is one file, but it runs under two libraries that agree on names and quietly disagree on details. A method that exists on torch tensors and not on numpy arrays works on the GPU and raises on the CPU. A 0-d value promotes to float32 under torch and float64 under numpy. A test would catch all of it, but you would maintain that test and that discipline for the life of the repo. It is the same shape of problem you are trying to remove, in miniature.

A correction made along the way

An earlier version of this analysis claimed the raw torch module could stand in as the array namespace with no adapter layer. The research pass showed that is wrong. SciPy and scikit-learn both go through array_api_compat, which patches about 90 torch names to fix scalar promotion, axis versus dim, and functions that return tuples. Raw torch misses 23 of the standard's functions. The standard also deliberately has no random number generation; scikit-learn draws in numpy and copies to the device, which would not work for our 500 Hz sensor noise on 1,024 robots. Option A would need the compatibility layer, strict-mode tests, and a two-backend random shim.

What B costs

Torch has a fixed overhead per operation that numpy does not. Two measurements, both on this machine's CPU:

One motor-law tick, ten elementary operationsµs
Python floats0.16
numpy on Python floats, which is today's CPU path1.8
numpy arrays of length 1, option A4.1
torch tensors of length 1, option B12.0
numpy arrays of length 74.0
torch tensors of length 711.6

The research agent measured a smaller gap on 12-element float32 tensors with one thread: about 0.5 to 0.8 µs per operation for torch, two to three times numpy, and at a batch of 1,024 torch wins. Either way a hundred-operation physics substep costs well under a millisecond, the policy loop runs at 100 Hz, and a whole CPU environment step should land at roughly twice today's cost because the physics engine and the Gymnasium loop are unchanged. Crossplay at a hundred thousand steps would gain about a minute. The CPU torch package is already installed in the default environment for reading checkpoints, so nothing new is pulled in.

Recommendation: B. Its cost is measured and small. Its precedent is direct. And it makes the CPU oracle and the GPU trainer execute the identical code path, not merely identical source: every rounding rule, every dtype promotion, every masked branch is the same object in both. A parity test can only sample that agreement. B makes it structural.

4 What the field does

Four research passes looked at how established robotics RL projects split engine code from plant code, and how they stop the observation pipeline from drifting between training, validation and the robot. Sources are in section 9.

The plan has three independent precedents

  • Isaac Lab and mjlab are option B. Their actuator classes take num_envs and device and hold [num_envs, …] state. The noise models are the same shape. Both frameworks run and test those classes at one environment on the CPU. Their reward and observation terms read only an engine-neutral data container, which is why Isaac Lab could swap its physics engine for Newton without rewriting a single term. [refs]
  • MuJoCo Playground is the same idea by a different mechanism. Noise, randomization, delays and reward are written as single-robot JAX functions. An outer vmap runs them at a batch of 1 or 4,096. One implementation, two scales. [refs]
  • Upkie's C++ spine is the sim-versus-robot half. One observer pipeline sits behind two interfaces, Bullet and the real hardware, so the observation dictionary is identical by construction. [refs]

What has no exact precedent is using the trainer's plant code as the CPU oracle. Nobody runs their training-time observation code on a robot either. We do not need to, because the firmware consumes only the ONNX file.

2 · the step is plain tensor math, no engine in sight

def compute(
    self, control_action: ArticulationActions, joint_pos: torch.Tensor, joint_vel: torch.Tensor
) -> ArticulationActions:
    # compute errors
    error_pos = control_action.joint_positions - joint_pos
    error_vel = control_action.joint_velocities - joint_vel
    # calculate the desired joint torques
    self.computed_effort = self.stiffness * error_pos + self.damping * error_vel + control_action.joint_efforts
    # clip the torques based on the motor limits
    self.applied_effort = self._clip_effort(self.computed_effort)

Isaac Lab, actuator_pd.py lines 186–195, IdealPDActuator.compute. The DC motor and the learned actuator nets are subclasses of this same class.

The Upkie cautionary tale

Upkie is the project whose reward shape we borrowed. Its C++ spine is the clean design. Then, from version 9, a Python PyBullet backend was added that rebuilds the same plant model, kept in sync "by convention". The C++ path applies gyro and accelerometer noise. The Python path does not. Nobody wrote that down as a decision. It is exactly a change-one-file-not-the-other outcome, in the project we learned from.

Two things stand out. First, the most common practice is the worst one, and it has post-mortems: humanoid-gym's sim2sim script omits the default-pose subtraction that training applies; go2-phoenix's audit found every export before a certain date had silently dropped normalization; rl_sar's joint order was wrong until a release fixed it. Second, our existing cross-engine parity tests are already ahead of common practice. The research found no other project with a test of observation assembly itself.

No project unifies the plant model, meaning motor, sensors, estimators and delays, across two engines. The field either randomizes over the mismatch or runs one plant. Option B goes further than the field there, which is fine, because it is the same technique applied one layer down.

One idea we had not considered

K-Scale traces a step(raw_sensors, carry) function into the ONNX, so the runtime feeds raw sensor values and the graph itself carries the scaling, the filters and the history. For us that would move the observation assembler out of the C firmware entirely. It is a real option for the last remaining drift surface, the C assembler on the firmware branch versus wlbot/obs.py. It also changes the export contract and sits on the firmware boundary, so it is a separate decision after this one, not part of it.

5 The proposed architecture

Option B lets the unification go one level higher than the models. The order of operations is also written twice today: the CPU env's step loop senses, ticks the yaw filter, pushes the delay ring, reads it, assembles, and keeps a two-step rate history for the jerk term. The mjlab actuator hook, the observation term and the reward term do the same sequence in three classes, with their own copy of that history. Change the sensor order in one and the other drifts, and no reward diff would show it.

So wlbot should own two pipelines, and each engine becomes a wrapper around them.

One policy step, from the inside

The policy acts at 100 Hz. Between two actions the physics engine and the plant model tick five times at 500 Hz, which is the firmware's own rate. Both pipelines run inside every substep; the observation is assembled and the reward scored once at the end.

Conventions the adapters would follow

Proposed, to be confirmed in the design step.

  • Every quantity is a tensor with a leading batch dimension, [n, …], even when n is 1.
  • Quaternions are (w, x, y, z), MuJoCo's order. PyBullet's adapter reorders at the boundary.
  • SI units at the policy boundary. Degrees inside the firmware estimators, as the firmware has them.
  • float64 on the CPU oracle, float32 on the GPU trainer, chosen at construction, as today.
  • One torch.Generator per environment for every random draw. Same seed, same episode, on both engines.
  • Domain randomization produces a params dict of tensors. Each adapter applies the plant fields its own way and hands the actuator and sensor fields to the pipelines.

6 How we get there

One model per commit. Before a torch twin is deleted, its existing parity test runs with the unified module in both slots. The old tests are the oracle for the migration itself, then they retire.

  1. Reward. The smallest file. Proves the pattern end to end.
  2. Motor, battery, leg servo, delay line. Measure the whole CPU environment step here and write the number down.
  3. Sensors and the observation delay ring.
  4. Pitch filter and the estimator model that wraps it.
  5. Yaw filter and its warm start.
  6. Observation assembler.
  7. Push wrench.
  8. Domain randomization draws, and the two single-robot backends switch from a perturbed config dict to the params dict.
  9. The sense and actuation pipelines, lifting the order of operations out of the CPU env and the mjlab hook so it exists once.

Tests afterwards

  • Deleted: the six model-parity tests in wlbot/cross_engine/ for the actuator, sensors, MDP, pitch filter, yaw filter and randomization. Their absolute-value checks, such as the analytic reward values and the encoder step size, move next to the modules they pin.
  • Kept: the model, passive-dynamics, PD-gate, linkage, obs-delay, environment and ablation tests. Those compare the two physics engines, which remains a real question.
  • New: nothing is required for the unification itself. A golden replay test that runs a recorded raw-sensor sequence through the pipelines and through the exported ONNX would be the field's best guard for the firmware boundary; we already keep hardware captures for the yaw filter.

7 Costs and open questions

  • The CPU tools get slower. Roughly twice per environment step by estimate. Step 2 of the migration measures it. If crossplay time ever matters, that is where to look.
  • wlbot depends on torch. The default environment already ships CPU torch. The firmware only takes the ONNX. Nothing in the deploy path changes.
  • Batched code reads less like a spec. where(acc_ok, …) replaces if acc_ok:. The firmware is the source of the estimators, not the target, and the docstrings keep the prose formulas.
  • CPU random seeds change. The GPU code is the surviving code, so GPU seeds keep reproducing. CPU seeds from before the migration will not, and the CPU is the oracle, not the trained artifact.
  • mjlab on device="cpu" still initializes CUDA unless the GPU is hidden. This touches only the single-robot MuJoCo backend on a machine without a GPU.
  • Isaac Lab's development branch is moving PD execution into the solver for speed. That is a counter-signal only if torch actuator overhead at 1,024 robots ever becomes the bottleneck, and mjlab's design shows it need not.
  • The firmware's C observation assembler is still a second copy of wlbot/obs.py. This plan does not touch it. The kinfer-style option in section 4 would, and is a later decision.

8 Words used here

plant
Control-engineering word for the thing being controlled, here the robot plus everything between the policy and the physics: motors, battery, sensors, estimators, delays. The physics engine simulates the body; the plant model simulates the rest.
oracle
A slow, trusted reference you compare the fast thing against. Our PyBullet environment plays that role for the GPU trainer.
batched, vectorized
Holding one column of numbers per quantity, one entry per robot, and applying every operation to the whole column at once. It is how a GPU simulates a thousand robots at the cost of one.
mask style
Branching with a column of true and false values and where, instead of an if. Needed because a thousand robots take different branches on the same line.
policy step, physics substep
The policy acts at 100 Hz. Between two actions the physics and the plant model tick five times at 500 Hz, the firmware's own rate.
sim2sim, sim2real
Checking a policy trained in one simulator inside a second simulator, and then on the real robot. Each transfer is a chance for the observation pipeline to differ.
domain randomization
Drawing a slightly different robot each episode: heavier, stickier wheels, weaker motor, later commands. The policy learns to cope with the spread instead of one exact plant.
parity test
A test that drives two implementations with identical inputs and asserts they agree. It catches drift after it happens.
delay line, zero-order hold
A ring buffer that returns the value from some milliseconds ago. Zero-order hold means it repeats the last value until a new one arrives, which is what real actuators and sensors do.
complementary filter
The firmware's way of estimating tilt: integrate the gyro for speed, pull gently toward the accelerometer's angle for stability. Both estimators here are ports of the firmware's own code.
ONNX
A portable file format for neural networks. The trained policy is exported to it and the firmware runs it. It is the only thing that crosses from this repository to the robot.
adapter, wrapper
A thin piece of code that translates between an engine's own API and the shared pipelines. It should contain no plant logic of its own.

Where the plan had to bend

  • The batched end-to-end eval became the acceptance check. Step 9a shipped two defects that both test suites, both PD gates and single-robot crossplay all missed: the pipeline added the IMU lever-arm velocity a second time, and the reset-time observation fallback reported zero pitch. Only the GPU eval gates on a strong checkpoint at a thousand episodes caught them, as a six-point survival drop. Every later step ran that check, with the pre-migration commit as the reference: survival about 0.79, velocity error 0.115, yaw error 0.32.
  • Three engine differences were resolved, not preserved. The reward scores live true state on both engines, where the CPU used to score a delayed reading. The sensor order is the firmware tick's. And imu_vel_world in the shared true-state dict means the IMU point's velocity, which each engine computes before handing it over.
  • mjlab's own actuator delay is switched off. The shared delay line models the action latency on both engines; the held-lag tests were rewritten against it.
  • Random streams changed on the CPU. Every per-episode draw now comes from one torch generator in a fixed order, so CPU seeds from before the migration do not reproduce. GPU seeds do.

What each package holds now

wlbot owns every model, both pipelines and the single-robot loop. wlbot_bullet is the URDF, the PyBullet backend and a Gymnasium wrapper. wlbot_mjlab is the MJCF, the single-robot MuJoCo backend, an actuator hook and the term classes that call the pipelines, plus training and evaluation. Its non-test code went from 3,596 lines to 2,344. The seven torch twins and the six model-parity tests are gone; the physics parity tests remain.

Still open: the C observation assembler on the firmware branch is the last second copy of wlbot/obs.py, and the kinfer-style export in section 4 is the candidate for it. Separately, wlbot/sysid/ was deleted earlier the same day as collateral of an unrelated move and awaits a decision on restoring it.
