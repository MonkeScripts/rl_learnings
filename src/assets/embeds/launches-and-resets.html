wlbot · lean_mdp · training throughput

Why the GPU was idle half the time

Our training loop runs 1024 robots on the GPU, and the GPU was only busy 46% of the time. This is the story of finding why, trying two fixes, and learning that the obvious one failed.

The symptom

A training iteration takes 2.9 seconds. We profiled one policy step (20.5 ms) and found this:

The sense tick alone issues 280 GPU kernels per substep. At five substeps per step, that is 1400 kernel launches from our code every 20 ms, plus another 275 from the actuation tick and 520 from the physics engine.

Each kernel is a small program. Launching it is a handshake: the CPU describes the work, packs the arguments, and sends it to the GPU. That handshake takes a few microseconds no matter how much work the kernel does. With 1024 robots, each kernel runs over about a thousand numbers, which the GPU finishes in under a microsecond. The handshake is longer than the work.

Two fixes target the two orange blocks in the step bar. The sense and actuation ticks, which we can rewrite, and the reset term, which fires whenever a robot's episode ends.

The ticks: kernel fusion

The idea

Most of our 280 kernels per substep are small: scale a tensor, add a bias, clamp a range, add noise. Each of these is its own launch. torch.compile traces the Python function, sees that five of those operations touch the same tensors in sequence, and merges them into one kernel that does all five. The number of launches drops from 280 to roughly 90, and the merged kernels are slightly faster because they keep data in GPU registers instead of writing it to memory between steps.

Think of it like this. Without fusion, the CPU is a manager who walks to the GPU's desk for every small task: "multiply this column by 0.8", walks back, "now add the bias", walks back, "now clamp to this range", walks back. With fusion, the manager writes a single memo: "multiply by 0.8, add the bias, clamp to this range" and makes one trip.

But first: clearing the roadblocks

torch.compile traces the function and builds a graph of its operations. Any line where Python asks the GPU for a value and waits for the answer breaks the graph into pieces. Each piece gets its own launch, defeating the point. We had four of these per substep, and each was a pattern like this:

pitch_filter.py — the pitch estimator decides whether to seed
if bool(self._pending.any()):        # "hey GPU, is anyone pending?"
    ids = self._pending.nonzero()    # "which ones?" (variable-length result)
    self.filter.reset(ids, ...)      # now operate on only those
m = self._pending                     # the mask stays on the GPU
seed_deg = static_seed_deg(...)       # compute the seed for everyone
f.pitch = torch.where(m, seed_deg, f.pitch)   # keep it only where pending
f.acc_angle = torch.where(m, seed_deg, f.acc_angle)
f.rejected = torch.where(m, torch.zeros_like(f.rejected), f.rejected)

The old version asks the GPU a question ("is anyone pending?"), waits for the answer, then builds an index of variable length. The compiler cannot predict the shape of that index, so it gives up and runs the rest eagerly. The new version computes the seed for all 1024 robots, which is a fixed shape the compiler can trace, and uses torch.where to keep the result only where the mask is true. Pending robots get exactly the same values. The rest keep theirs. No question asked, no waiting.

The same pattern appeared in three more places:

latency.py — the observation delay ring fills unfilled slots
fill = ~self.filled
if bool(fill.any()):                     # wait for the GPU
    self.buf[fill] = frame[fill].unsqueeze(1).expand(...)   # variable shape
    self.filled = torch.ones_like(self.filled)
self.buf = torch.where(fill[:, None, None], frame[:, None, :], self.buf)
self.filled = torch.ones_like(self.filled)
actuators.py — motor noise check
noise = self.torque_noise.unsqueeze(-1)
if bool((noise > 0.0).any()):            # asks the GPU every substep
if self._noisy:                          # decided once at startup, from the config
    tau = tau + noise * torch.randn(...)

The noise level is a config constant. Asking the GPU whether it is nonzero 25,000 times per iteration is 25,000 round trips with a known answer.

The wrapping

With the roadblocks gone, the compile call is two lines in the GPU actuator hook, where the trainer calls the ticks:

mjlab_wheel_actuator.py — compile at initialisation
self._sense_tick = torch.compile(self.sense.tick, dynamic=False)
self._pipe_tick = torch.compile(self.pipeline.tick, dynamic=False)

The models themselves know nothing about compilation. The CPU single-robot path calls the same methods eagerly. The parity between the two paths is a test, not an assumption.

The idea that failed: CUDA graphs

Fusion merges nearby operations into fewer kernels. A CUDA graph goes further: it records the entire sequence of launches once, then replays the whole recording with a single instruction from the CPU. Every launch becomes free after the first run.

Here is the concept. Imagine you are directing a play. Without a graph, you call out each lighting cue and each sound effect one at a time from the booth: "lights down", wait for confirmation, "sound effect 3", wait, "spotlight on". The crew is fast, but half the show is you talking to them.

A CUDA graph records which kernels run, in what order, reading from which memory addresses and writing to which others. On replay it issues the whole sequence with one instruction. The crew runs the lighting cues back to back with no pauses.

The catch: the recording is literal about memory. If a tensor lived at address 0x7f00 during recording, the replayed kernel reads from 0x7f00. If that tensor was freed and a new one allocated at 0x7f10, the kernel reads stale data at the old address. PyTorch handles this by copying every moved tensor back to its recorded address before each replay.

In our ticks, nearly everything moves. The actuator hook builds a fresh dictionary of seven true-state tensors every substep, and the sensor models update their state by writing self.pitch = new_pitch, which in Python creates a new tensor at a new address. So before each replay, PyTorch copies seven inputs and about forty state tensors to their recorded positions. At 1024 robots, those copies cost about as much time as the 280 launches the graph was supposed to remove.

The graph mode was tried, measured, and removed from the codebase. The comment in the actuator hook says what happened and why, so the next person who reaches for reduce-overhead knows what to fix first: make the state tensors in-place (write into existing buffers rather than creating new ones, about 43 assignment sites across six files) and stage the inputs into fixed buffers. That is a wider edit and it was not the one we needed today.

Fusion alone delivered 11% off the iteration. We kept that.

The resets: fewer instructions for the same job

The problem

When a robot's episode ends, the ResetRobot event draws new physical parameters (motor constants, masses, friction, wheel radius) and writes them into the MuJoCo model. This costs 2.1 ms per call, whether one robot resets or 128. The cost is flat because it is made of about 380 kernel launches, not 380 units of computation.

With episodes about 900 steps long, one or two of the 1024 robots reset almost every step. So the reset term fires nearly every step and adds a steady 2 ms to a 20 ms step.

What we changed

Before touching code, we profiled the reset section by section. The four-bar kinematics round trip, which had looked like the obvious waste (data goes GPU to CPU, through numpy, back to GPU), turned out to cost 0.13 ms. The sync itself was 9 microseconds. The cost was in the writes, not the transfer.

events.py — mass and inertia: three groups became one write
for key, gids in self.mass_group_ids.items():
    ge, gb = torch.meshgrid(ids, gids, indexing="ij")
    nominal_mass = env.sim.get_default_field("body_mass")[gids]
    model.body_mass[ge, gb] = nominal_mass * factor
    model.body_inertia[ge, gb] = nominal_inertia * factor
                 ↓ three loops × (meshgrid + 2 reads + 2 writes) = 15 launches
factor = torch.stack([fac[k][:, c] if fac[k].dim() == 2 else fac[k]
                      for k, c in self.mass_layout], dim=-1)
rows = ids[:, None]
model.body_mass[rows, self.mass_bids] = self.nominal_mass * factor
model.body_inertia[rows, self.mass_bids] = self.nominal_inertia * factor
                 ↓ one stack + 2 writes = 3 launches

The per-group loop ran three times (base, leg, wheel), each time building index tensors with meshgrid, reading the nominal values from the model, and writing the scaled result. The new version builds one flat index tensor in __init__, reads the nominals once at construction, and writes each field with a single indexed assignment.

The height had to reach the CPU for the four-bar kinematics anyway. We sent all five scalars over in one stack, built the whole 13-column root state in numpy with the same formulas, and uploaded it in one tensor. The kinematics is called exactly as before.

What we learned

Both estimates were too high, and for the same reason. Each assumed the largest visible item was the cost, and the finer measurement said otherwise. The kinematics round trip looked like the obvious waste in the reset and turned out to be 6% of it. The CUDA graph looked like the obvious tool for a launch-bound loop and turned out slower than plain fusion. The habit that paid was measuring one level deeper before editing.

What worked

  • Kernel fusion via torch.compile, merging small operations into bigger kernels.
  • Replacing host syncs with masked torch.where, so the compiler can trace the whole function.
  • Batching indexed writes into one per model field instead of one per group.
  • Building the spawn pose on the host alongside the kinematics that was already there.

What did not

  • CUDA graphs. The tensor copies before each replay cost as much as the launches removed. Would work after making all state in-place (~43 sites), which we chose not to do.
  • Optimising the kinematics transfer. It was 0.13 ms. The rest of the reset was ten times more.
