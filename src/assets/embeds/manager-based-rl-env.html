ManagerBasedRlEnv

How ManagerBasedRlEnv assembles the wlbot task

The config objects, what each manager does, and when each piece runs.

The three YAML files become one env

make_env_cfg() in sk_env_cfg.py reads three config files, merges them, and builds a single ManagerBasedRlEnvCfg that mjlab instantiates as the training environment.

The config merge

make_env_cfg() runs at task registration time. It reads the three YAML files and merges them into one ManagerBasedRlEnvCfg. The merge order matters:

sim_default.yaml The robot. Geometry, motor constants, IMU parameters, servo model, engine-specific solver settings. This is the plant.

train_sk.yaml The sim: block overrides parts of sim_default (pitch filter on, action delay range). The merge is recursive, so nested keys are patched, not replaced.

randomization.yaml DR ranges for every plant parameter. Masses, friction, motor constants, battery voltage, sensor biases, push forces.

train_sk.yaml The rand: block overrides parts of randomization (pins commands to zero, narrows the height band). One-level merge per top-level key.

train_sk.yaml directly provides: reward weights and schedule, PPO hyperparameters, curriculum warmup fraction, observation config (history depth, height_action flag).

train_legs.yaml uses inherit: train_sk and overrides only legs-specific keys: obs.height_action: true, sag and CoM randomisation, a tighter schedule.

The six managers

Each manager is a named dict in the cfg. mjlab creates the manager, which creates each term from its cfg, and calls them at the right moment during env.step().

Action Manager 100 Hz

actions = {"wheels": WheelVoltageActionCfg(n_actions=2 or 3)}

Called once per policy step. process_actions() clips the policy output to [-1, 1] and calls pipeline.mix() to store the mixed voltage command. This is where the neural network's output enters the system.

The action term finds the ActuationPipeline through wheel_actuator(entity).pipeline, which looks up the actuator hook on the robot entity.

Observation Manager 100 Hz

Two observation groups, each a dict of terms:

GroupTermsWidthWho sees it
actorStationKeepObs32 or 40The policy network
criticStationKeepObs + PrivilegedState + PlantParams59 or 68The value function (training only)

Called after all substeps. StationKeepObs.compute() calls sense.observe() on the actuator hook's SensePipeline, which assembles the frame-stacked, scaled observation vector.

Reward Manager 100 Hz

rewards = {"station_keep": RewardTermCfg(func=StationKeepReward, weight=1.0, params={...})}

Called before observations within each step. Computes the product-form reward from true pitch (not sensed), odometry position error, and yaw error. Reads the curriculum level from the shared DomainRandomizer and applies the reward schedule.

The params dict carries sim_cfg, the reward weights, and the schedule. These are baked at construction time.

Termination Manager 100 Hz

TermCondition
time_outEpisode reaches episode_length_s (truncation, not failure)
fell_over|pitch| or |roll| exceeds the fall angle
runaway|wheel speed| exceeds 125 rad/s
pos_runaway|pos_err| exceeds the guard distance

Command Manager resampled

commands = {"base_velocity": VelocityYawCommandCfg(cmd_vel_range=[0,0], cmd_yaw_rate_range=[0,0])}

Draws a velocity and yaw-rate command, held for 2 to 4 seconds, then resampled. In the current training configs both ranges are [0, 0], so the command is always "stay still." The observation and reward terms read the command through env.command_manager.get_command("base_velocity").

Event Manager reset + step

TermModeWhat it does
reset_robotresetDraws DR parameters, writes them into the MuJoCo model (masses, friction, wheel radii), sets the initial pose, resets the servo and both pipelines
pushstepOwns its own per-env timing. Fires a horizontal force at a random offset point, holds it for the push duration, clears it when expired. Clears on reset so forces never leak across episodes.
curriculumstepRamps the push force cap and init-state spread from 0 to full over warmup_fraction of training. Writes dr.curriculum which the reward schedule also reads.

The actuator hook (not a manager)

WheelVoltageActuator hooks.py 500 Hz

Registered on the robot entity through EntityArticulationInfoCfg.actuators. Not a manager term. mjlab calls it at the physics substep rate (5 times per policy step).

This is the only code that runs at 500 Hz. It exists because the motor law and sensor filters need the substep rate, and the actuator hook is the only framework entry point that runs there.

MethodWhenWhat it does
compute(cmd)Before each substepReads cmd.vel (wheel speeds from MuJoCo), calls pipeline.tick(omega) (delay line, battery sag, motor law), returns torques. Also writes hip servo targets when the height action is on.
update(dt)After each substepReads joint state from MuJoCo (qpos, qvel, quaternion), packs it into a sensor dict, calls sense.tick() (pitch filter, encoder LPF, sensor noise). The sense pipeline is here because there is no other 500 Hz hook.
reset(env_ids)On episode resetResets both pipelines: redraws action delay, zeros the delay ring, re-latches battery voltage.

The actuator hook creates and owns both the ActuationPipeline and the SensePipeline. Other terms access them through the wheel_actuator(entity) lookup function, which finds this object on the robot entity.

One policy step, in order

When the trainer calls env.step(action), mjlab runs these in sequence:

1. event manager     (step mode)    push timing, curriculum level
2. action manager    (100 Hz)       process_actions → pipeline.mix(action)
   ┌─── substep 1 of 5 ──────────────────────────────────────────┐
   │ 3a. actuator compute  (500 Hz)  pipeline.tick → torques     │
   │ 3b. MuJoCo physics              apply torques, step 2 ms    │
   │ 3c. actuator update   (500 Hz)  sense.tick → sensor filters │
   └─────────────────────────────────────────────────────────────┘
   ... substeps 2 through 5 repeat 3a-3b-3c ...
4. reward manager    (100 Hz)       station_keep_reward(true_pitch, ...)
5. observation mgr   (100 Hz)       sense.observe → [1024, 32 or 40]
6. termination mgr   (100 Hz)       fell_over, runaway, pos_runaway
7. command manager                  resample if hold timer expired

What gets baked at construction

Some config values are read once when ManagerBasedRlEnv(cfg) is called and cannot be changed afterward. Others are drawn per episode by the event manager.

Baked at constructionDrawn per episode (events.py)
Action delay range (min/max lag)Action delay (exact ticks, from the range)
Pitch filter coefficientsMotor constants (kt, ke, Coulomb, viscous)
Sensor noise standard deviationsMasses, friction, wheel radii, battery voltage
Reward weights and scheduleInit state (pitch, height, velocity)
Solver iterations and contact limitsPush force, timing, direction
Encoder velocity filter cutoffLeg sag, fore-aft CoM shift (legs config)

This is why make_env_cfg() takes optional sim_cfg and rand_cfg arguments. Evaluation with --clean passes ablated configs that strip pushes, noise, and DR. The ablation must happen before construction, not after, because the baked values would not change.
