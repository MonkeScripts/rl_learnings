Float against int16

We built the same neural network two ways on an ESP32 and measured both on the robot. The quantized one is 3.5 times slower and cannot hold the control rate.

ESP32 240 MHz, 32 KB I-cache 40 → 64 → 64 → 2 tanh network 100 Hz policy rate 2026-09-10

The two approaches

Both run the identical trained actor at 100 Hz on a task below the 500 Hz control tick, take the same 40-number observation, and produce the same two voltages. Everything after the arithmetic is shared.

Approach A

Hand-emitted float C

A code generator reads the published actor and writes out three matrix loops with tanhf between them. Weights are float32 forced into DRAM. No library, no interpreter, no build step beyond the C compiler.

Approach B

esp-ppq int16 through esp-dl

esp-ppq quantizes the actor to 16-bit weights and activations, calibrated on real observations from a flight capture, and folds both tanh layers into 2049-entry lookup tables. esp-dl loads the graph and executes it node by node.

The one column int16 wins is memory, and it wins it in the wrong currency. Its graph sits in flash, which is 59% empty on this board. The float weights sit in DRAM, which is the scarce resource. That trade is real and it is the only argument left on this chip.

Why the quantized one lost

Three causes, and none of them is a tuning problem.

The chip already has a float unit

16-bit arithmetic pays off where a vector unit does eight of them at once. The original ESP32 has no 16-bit vector instructions and does have a single-precision float unit, so each quantized operation is at best the same speed and carries quantize and requantize steps the float version never runs.

An interpreter around a very small network

esp-dl walks a graph: it dispatches per node, tracks tensors, and requantizes between layers. Spread over a large convolutional model that overhead disappears. Spread over three matrix layers it is most of the work, which is how 435 µs of arithmetic became 1,201.

Far more code through the same small cache

The float path is 382 bytes of code. esp-dl brings tens of kilobytes of interpreter and kernels, and all of it streams through a 32 KB instruction cache that the control tick, the motor commutation and the radio evict between every inference. That is why a cold cache costs 929 µs on one path and 7,451 on the other.

Where it leaves us

The robot goes back to the float path. int16 through esp-dl is slower at every measurement we took, and slow enough that the policy stopped running at the rate it trained at.

The two changes actually worth making are the ones the profiler pointed at before quantization entered the picture. Approximating tanh in the code generator is worth 255 µs of the 435, since those 128 library calls cost more than all 6,784 multiply-accumulates put together. Moving the forward pass into RAM addresses the 929 µs of cache misses. Neither adds a dependency and neither costs the bit-exact replay gate.

The esp-dl work stays in the repository behind its own switch. The ESP32-S3 and P4 have the 16-bit vector kernels this chip lacks, so the same measurement on either could come out the other way. On this board it does not.
