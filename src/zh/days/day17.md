**目标：** 把训练好的策略导出来，让它在微控制器上跑进时间预算，并且在信任它在机器人上的任何表现之前，一步一步验证它。

## 接着上回

第 16 天停在板子上：延迟范围是在台架上定的，可一到部署，延迟就由芯片说了算，推理时间、发布延迟、量化都算在里面。轮足机器人的 actor 训练时动作延迟从 5 到 30 ms 里抽，到了真机上实际是 6 到 9 ms。那么，要怎样才能把策略跑在芯片上，又不改变它训练时面对的那个对象？

这堵墙，早有人撞过几块。2017 年，Facebook 和微软发布了 ONNX：一种能被任何运行时读取的网络计算图格式，因为当时每个框架都有自己的格式，而没有一个能跑在目标硬件上。2018 年，Google 的 Benoit Jacob 等人展示了只用整数运算跑网络的方法，目标是让卷积网络在手机 CPU 上跑得快；从那以后，“想塞进小芯片就量化”几乎成了默认建议。在足式机器人这边，Hwangbo 等人 2019 年把 RL 策略直接跑在 ANYmal 自己的机载计算机上，并且把学出来的执行器模型放进训练回路，让策略在仿真里看到的对象就是它将来要面对的那个。

我们的芯片是一颗 240 MHz、指令缓存 32 KB 的 ESP32，还要和一个 500 Hz 的平衡回路共用一个核。第一次尝试是最直白的那种：先把网络从 GPU 上搬下来，再把它变小、变快。

## 打个比方

我在关于 `.pt`、`.onnx`、`.engine` 的笔记里用过一个比方，现在还挺喜欢。`.pt` 检查点像 Word 文档：好改，但打开它得装上整个 Word（PyTorch、Python、一个 G 的库）。ONNX 像 PDF：定了型，几乎在哪儿都能打开。编译好的 engine 像印好的书：读起来最快，但只为一个读者印。

最直白的计划就顺着它来：导出 PDF，然后用读者能看清的最小字号印成书，字小页数就少，页数少读得就快。

它在两处会断。字小读得快不快，取决于读者的眼睛，而我们这位读者恰好没配那副眼镜。另外，机器印出来的书，可能和原文说的不是一回事，而每一页看上去都没毛病。不过第一个问题比这两个都早：我们的读者根本打不开 PDF。

## 一步一步来

### 先把网络从 GPU 上搬下来

一个训练好的 rsl_rl 检查点里有 actor、评论家网络（critic）、优化器状态和观测归一化器。真正上车的只有 actor。评论家和 GPU 都留在后面：在机器人上跑的，是一个 40 → 64 → 64 → 2 的 tanh MLP，每次决策 6,784 次乘加。

最直白的跑法，就是训练时的跑法：加载 `.pt`。这需要 Python 和 PyTorch，而机器人是一块微控制器。下一个直白的办法，是在芯片上放一个读 ONNX 的运行时。可那意味着一个解释器、一个加载器、几十 KB 的代码，挤进一块 RAM 本来就最紧张的板子。

我们的做法是：一个 Python 脚本读取发布出来的 actor，生成一个把所有权重都写死的 C 文件，三层矩阵循环，层与层之间夹一个 `tanhf`。没有库，没有解释器，除了 C 编译器没有别的构建步骤。权重是 float32，强制放进 DRAM，27,656 字节，正好等于 $4 \times (40 \cdot 64 + 64 + 64 \cdot 64 + 64 + 64 \cdot 2 + 2)$。推理路径上的代码只有 382 字节。

$$
\begin{aligned}
\text{MACs} &= \textstyle\sum_{\ell} n_{\ell-1}\, n_\ell \\
&= 40 \cdot 64 + 64 \cdot 64 + 64 \cdot 2 = 6{,}784
\end{aligned}
$$

::: tip
每一层把每个输入和每个输出各乘一次。要记住的是：只有第一层看得到观测。输入加宽，只有这一项会涨。
:::

导出时还捎带着两个决定。第一个是归一化器放哪。Microduck 的导出器把它烧进 ONNX，这是 rsl_rl 和 Open Duck 的习惯。我们的 runner 把它留在 C 里、网络外面，原因在第 5 拍。第二个是观测组装器：固件用自己的 C 代码拼出这 40 个数，于是 `obs.py` 有了两份，一份 Python，一份在芯片上：正是第 15 天留着没解决的那份第二副本。

::: field 实战笔记：导出要带上什么
**要带：** 只带 actor，外加归一化器的均值和尺度。**要钉死：** 常数钉在训练时相信的值上，而不是你重新量出来的值。里程计用的是名义轮半径 0.019205 m，10 ms 的步长烧进了组装器的滤波器。重新量一次轮子，不能悄悄改掉策略对距离的感觉。**会出什么错：** C 观测组装器是对象代码最后一份“第二副本”，没有任何东西让它在结构上保持一致。rl_toys 缺陷清单里的 SAF-9：主机端加载器从没断言观测归一化是关着的，于是可能悄悄做了两次归一化。**仍未解决：** 生成权重的那个脚本本身不在我的笔记里，试用期报告只记录了它存在于 `lean_deploy` 分支。
:::

网络就这样以纯 C 跑起来了。profiler 上算术花 435 µs，周期是 10 ms。看着慢得值得优化一下，而教科书对“慢”的标准答案是量化。

### 为了快去量化，结果更慢了

教科书说，16 位整数只有浮点的一半大，搬的内存少一半，算术也更便宜。于是 esp-ppq 把 actor 量化成 int16 的权重和激活，用一次飞行采集里的真实观测做校准，并把两层 tanh 折成 2049 项的查找表。esp-dl 加载这张图，一个节点一个节点地执行。

在初代 ESP32 上，它慢了 3.5 倍。

| 指标 | 浮点 C | int16 esp-dl |
|---|---|---|
| 算术，热缓存 | 435 µs | 1,201 µs |
| 推理窗口，最小值 | 1,364 µs | 8,652 µs |
| 推理窗口，中位数 | 3,075 µs | 10,722 µs |
| 策略间隔，中位数 | 10.0 ms | 11.0 ms |
| 超过 15 ms 的间隔 | 0 | 50 |
| 到达轮子时的动作年龄，p99 | 8 ms | 13 ms |
| 电机指令最大误差 | 0.003 mV | 72.3 mV |

一半的 int16 推理比它该塞进去的周期还长，策略于是不再以训练时的频率运行。原因有三个，没有一个是调参能解决的。ESP32 有单精度浮点单元，却没有 16 位向量指令，所以一次 int16 乘法最多和浮点一样快，还要多出量化、反量化的步骤。esp-dl 是解释器，它每个节点的开销放在大卷积模型上看不见，放在三层矩阵上却是大头。再加上 esp-dl 带来几十 KB 的代码，要挤过同一个 32 KB 的指令缓存，而控制节拍、电机换相和无线电在两次推理之间会把它清空：冷缓存在浮点路径上多花 929 µs，在 int16 上多花 7,451 µs。

int16 唯一赢的一栏是内存，而且赢的是不值钱的那种。它的图放在 flash 里，这块板子的 flash 还空着 59%。

后来同样的实验在 ESP32-S31 上用 Microduck 的策略又做了一遍：61 → 512 → 256 → 128 → 14 的 ELU 网络，196,864 次乘加，50 Hz。答案翻了过来。

| Microduck actor，ESP32-S31 | 平均延迟 | 塞得进 20 ms？ |
|---|---|---|
| ESP-DL int16 | 4.2 ms | 是 |
| 纯 C 浮点，权重在 PSRAM | 9.9 ms | 是 |
| 纯 C 浮点，权重在 flash | 48.3 ms | 否 |

S31 有 16 位向量核，这个网络也是另一类问题：772 KB 的浮点权重放不进 512 KB 的内部 SRAM，所以纯 C 卡在内存带宽上，而不是浮点单元上。ESP-DL 的 int16 权重只有一半大，内核还用 SIMD 读取。芯片上的输出和浮点参考的平均绝对误差是 0.0011。

::: field 实战笔记：int16 还是浮点
**该量化：** 芯片有 16 位 SIMD，且浮点权重放不进快内存。S31 上的 Microduck，4.2 对 9.9 ms。**留在浮点：** 芯片有浮点单元、没有向量单元，网络只有几层小矩阵。ESP32 上的轮足机器人，1,201 对 435 µs。**会出什么错：** 量化新增了校准范围、图的读取、舍入这几种出错方式（第 5 拍），所以它总得换回点什么。**现状：** 机器人退回了浮点路径，esp-dl 留在仓库里，用开关隔开。“初代 ESP32 没有 SIMD”只是怀疑的原因，试用期报告仍把确认它列为待办。
:::

所以量化回答的是一个我们没问的问题。int16 图只会碰到矩阵运算，而在浮点路径上，时间根本不花在那儿。

### 3 毫秒去哪了

不是乘加，那是什么？有两个工具在量浮点网络的开销，结果差了三倍。飞行记录器给每次推理打上墙钟时间：8,769 次推理的中位数是 3,075 µs。控制台 profiler 把前向连跑 200 次，报 435 µs。

直白的读法是把记录器取个平均，说开销是 3 ms。可这块芯片上每个计时样本都是真实开销加上打断它的东西，而打断只会往上加。分布有一个硬底和一条长尾，所以均值是“打断”的均值，会随负载变。样本够多时的最小值，才最接近开销本身：1,364 µs。两个工具量到的都是底，所以它们之间的差是真的，下面五层嵌套就是把它拆开。

  <iframe src="../../assets/embeds/where-the-3-milliseconds-go.html" title="3 毫秒去哪了：一次推理按比例拆开" loading="lazy" style="height:900px"></iframe>

$$
\begin{aligned}
t_{\text{arith}} &\approx N_{\text{MAC}}\, c_{\text{MAC}} + N_{\tanh}\, c_{\tanh} + N_{\text{in}}\, c_{\div} \\
&= 169 + 255 + 11 = 435\ \mu\text{s}
\end{aligned}
$$

::: tip
在这颗芯片上，一次 tanh 要 1.99 µs，约等于 80 次乘加。128 次 tanh 比全部 6,784 次乘加还贵。而算术只占一次真实推理的三分之一：1,364 里有 929 µs 算术解释不了，我把它归到 flash 指令缓存缺失上。这是归因，不是读数。
:::

于是按真实的 1,364 µs 给几个杠杆排个序：把前向搬进 RAM（最多 929 µs，约 340 字节）；在代码生成器里近似 tanh（255 µs，但得先定好 2e-4 的回放容差）；量化成 int16（最多 169 µs，代价前面已经看到了）。前两个都还没试。

试试你自己的网络。下面的成本来自这一页上的实测，每颗芯片一个网络，所以离那些网络越远就越是外推，小部件会直接告诉你。

把芯片切到 int16、100 Hz，条形就越过周期线，和机器人上一样。点 14 帧的预设：乘加大约翻倍，从约 6,800 到 13,200，照样轻松塞下。再把 Microduck 放到 S31 的两个选项上看看。

::: field 实战笔记：在微控制器上给策略计时
**用最小值，不用均值**，并且写明每个数来自哪个工具。**会出什么错：** profiler 第一次跑时给组装器喂了全零的观测，而 `tanhf` 对很小的参数会提前返回，于是它量的是便宜的那个分支，一步读出来比里面的前向还快。现在它改用真实采集里开销中位数那一行。**仍未解决：** tanh 近似和 RAM 实验都没测过；而能证实或推翻缓存归因的，正是 RAM 实验。
:::

拆解里有一行比计算本身还大：中位窗口里有 1,711 µs，是策略被 500 Hz 的控制节拍抢占掉的。这不是该优化掉的 bug。这是故意的。

### 策略永远不能拖慢平衡

最直白的放法，是把策略塞进控制回路：读 IMU，跑网络，写电机。500 Hz 下一个节拍只有 2,000 µs。浮点推理的中位数是 3,075，于是每一个策略步都会让平衡回路错过截止时间，而倒立摆错过截止时间，就是摔倒。

所以固件把两者分开。控制节拍以 500 Hz 跑在 core 1、优先级 20，从不等策略。每到第五拍，它把一份传感器快照投进邮箱，然后接着干活。策略任务在同一个核上、优先级 19，只能在节拍留下的空隙里运行。它的输出带着 `t_ms` 时间戳从邮箱回来，这个时间戳就是陈旧时钟：输出超过 60 ms 就当作数据断了，PD 律收回轮子。

交出轮子也一样有门。DISARMED、REFLEX、HOME、YAW、DISTURBED、HEIGHT、STALE，每一道都能拒绝或撤销一次授权；500 ms 的斜坡让电压从零升起来，6 V 的上限兜住它，不管网络要多少。没有备用网络。如果图算出一个非有限的动作，runner 什么都不发布，下一拍 STALE 触发，PD 接手。`espdl_fb` 计数器负责把这种情况和数据断流区分开。

同样的分隔在 Microduck 上高了一层：一个技能一个 ONNX 文件，由基于规则的多路器切换。走路和前滚翻从不共用一个网络，因为“一半走路一半翻滚”不是一种行为。

::: field 实战笔记：安全层
**规则：** 策略提议，固件拍板。频率、优先级、陈旧时钟、斜坡、上限、高度门都放在网络外面，坏网络跟它们讲不了价。**会出什么错：** 早先的主机回路把它们放错了地方。SAF-2：NaN 直接穿过导出 C 的输出钳位进了混合器。SAF-5：±inf 穿过了固件的 NaN 过滤。SAF-1：主机端主动绕过了固件看门狗，遥测丢了也察觉不到。SAF-4：授权斜坡只上膛一次，之后再不重新上膛。**怎么测：** 给 runner 喂一个 NaN，确认没有任何东西到达电机，并且 STALE 触发。
:::

这样的布局能防止坏策略伤到机器人。可它不会告诉我们，芯片算的是不是我们训练的那个策略；而一个算错了、又老老实实待在 6 V 以内的网络，看上去和一个坏策略一模一样。

### 验证阶梯

最直白的检查是刷进去，看它能不能站。这个检查分不清是移植错了还是策略错了，所以 runner 设了四道关，每一道都去比上一道够不着的东西。

| 关卡 | 比什么 | 容差 | 抓到过什么 |
|---|---|---|---|
| 1. ONNX 回放 | 我们的读取器对 onnxruntime，512 个观测 | 1e-5 | 一个 64×64 的方阵层没转置：下游自洽，动作差 1.27 |
| 2. 黄金回放 | 生成的 C（主机 gcc）对 numpy 孪生，240 步连续 | 动作 2e-4，电压 1e-3 V | 目前 3.3e-7 通过 |
| 3. 量化评分 | int16 对浮点，整段真实采集，按越界行拆分 | 越界行为 0 | 下面那次校准失败 |
| 4. 片上向量 | 32 个观测在 ESP32 本身上评分 | 对 esp-ppq 整数孪生 2e-4，对浮点 6.7e-3 | 唯一碰得到芯片自己算术的一关 |

第 1 关听上去多余，直到它报警。一个方阵层行列读反了，仍然是合法的 64×64 矩阵，每个形状检查都能过，而网络错得比它输出本身的幅度还大。

第 3 关是归一化放在图外面的回报。把归一化折进第一层，等于把四十个原始范围跨三个数量级的通道交给量化器，让它们共用一个 16 位尺度。就算避开了这一点，校准范围也决定了图能表示哪些观测，范围之外的一律被截断。

::: field 实战笔记：给量化网络打分
**出过的错（2026-09-09）：** 一个步数上限让校准器只看到 90 s 运行里的前 10 s。它把范围定成 ±0.25，而这次运行到过 0.695；4.8% 的行有通道被截断（动作回灌和陀螺仪都在其中），量化网络和浮点网络最多差 7 V，机器人肉眼可见地飞得更差。**修法：** 在整个窗口上取 minmax，并强制放进幅度最大的几行；导出器打印越界行数，必须为零。修完后：最大误差 72.3 mV，99 分位 43 mV，信号本身的散布是 570 mV。**评分器还先骗过一次：** 早先的版本只给留出的尾段打分，那正好是整段里最安静的一截，对一个在关键处差 0.87 的网络报了 1.16e-3。整段采集都要评。
:::

扯远了，先回顾一下，因为刚才是五拍的管道活。芯片背不动运行时，所以我们把 actor 导成纯 C。为了快试了 int16，结果它在 ESP32 上更慢、在 S31 上更快，因为快不快是芯片说了算。我们找到了时间真正花在哪，大部分根本不是算术。我们把策略放在平衡回路下面，挡在一排不信任它的门后面。我们还搭了四道关，每一道抓一种“芯片算的不是那个网络”的方式。它们全都在拿芯片和网络比。没有一道能告诉我们，这个网络能不能让机器人站住。

### 第一次刷机：40 mm 站得住，70 和 85 打满

第一次上硬件的 `sk_head_yd15_r128_s0`（2026-09-02），就是第 13 天讲自锁时用的那次。这里从部署这一侧再看一遍，看的是排查顺序。40 mm 蹲着的时候它站住了：138 个样本全归它，晃得厉害，电压在 −8 到 +5 V 之间来回甩。70 和 85 mm（训练高度）时，接手第一拍就打满，PD 每次都把轮子收回去。

最直白的嫌疑人是移植。它最先被排除，这正是第 5 拍的意义：C 推理链在 240 步黄金回放上和 PyTorch 的动作误差是 4.1e-7，固件和仿真的几何与接口一致，对 actor 的离线探针在直立附近符号也对。所以问题只能落在固件或权重上。

然后是两条错路。70 mm 的影子看上去很健康，约 1 V，这就是第 13 天讲过的陷阱：`pos_err` 一直在抵消俯仰项，直到接手时被复位清零。俯仰修正扫描在 −6° 把影子输出调到零，结果接手时策略打向了另一条轨。它只是换了一条轨，所以不是静态偏置。把陈旧窗口从 60 ms 放宽到 200 ms，什么都没变，这证伪了“是弹出阻止了它站住”。

联合诊断找到了两个确认的原因。

1. **固件：授权那一拍执行了过期的副本。** 控制节拍先拷贝策略邮箱，再处理授权，所以回合复位从没让节拍里那份本地副本失效。仲裁器用复位前的影子输出驱动了一个 2 ms 节拍，然后又把它当陈旧弹掉。五次授权有四次恰好死在一拍里，跟陈旧窗口多大无关。已修：授权现在会让本地副本失效。
2. **策略：第 13 天那个经由 prev_action 的自锁。** 对刷进去的权重做静态探针，收敛到 (+8.00, +1.04) V，和影子输出钉死的值残差 0.000 V。

::: field 实战笔记：先排除管道
**顺序：** 先数值移植，再固件，再策略。移植验证过之后落在策略上的发现，是给训练那边的需求，而不是一场调试。**重训落地前先上线的：** 授权修复；接手上限和斜坡（6 V、0.5 s），让锁死的满电压到不了电机；高度门设为训练范围 45 到 85 mm。**重训验收：** 在中性状态下从 `prev_action = ±1` 做静态探针，输出低于 2 V。**仍未解决：** 真机上的一致性还没评分，因为现有采集缺了评分器需要的上电边沿；下次上台架要在上电之前就开始采集。
:::

固件 bug 修好了，自锁要靠重训。剩下的问题是为什么而重训，因为板子已经告诉了我们它的延迟，而那不在训练放它的位置上。

### 频率不是旋钮，更快也不是更好

最直白的做法是把省下的时间花掉：推理最快只要 1,364 µs，那就用同一组权重跑 200 Hz，把延迟减半。

这组权重不知道怎么在 200 Hz 下被运行。10 ms 的步长烧进了组装器的滤波器，四帧堆叠跨三个间隔，所以网络学到的“一帧之前”是以秒计的。到了 200 Hz，同样的权重看到的参考量以一半的速度漂移，历史也只剩一半。这就出了分布；换频率就得重训。

频率不变、只让推理更快，也是同一个问题，只是安静一点。actor 训练时的动作延迟从 5 到 30 ms 里抽，机器人上量到的是 6 到 9：它已经飞在训练分布偏快的边上了。再从推理里省 2 ms，只会离训练分布更远，而不是更靠近中间。另外，输出要保持五个节拍直到下一次推理，所以策略掌舵时，这真的就是一个没有快速内环的 100 Hz 平衡控制器。

$$
\begin{aligned}
d_{\text{robot}} &= t_{\text{infer}} + t_{\text{publish}} + t_{\text{hold}} \\
d_{\text{robot}} &\in \operatorname{supp}\big(p_{\text{train}}(d)\big)
\end{aligned}
$$

::: tip
机器人实际承受的延迟，是由芯片自己的各项时间加起来的。不管你对芯片做什么，这个和都得留在策略训练过的范围里，最好靠近中间。
:::

移植之后变的正是这个。消融那批 run 的延迟从 5 到 45 ms 里抽；为了 ESP-DL 移植，窗口改成了 3 到 30 ms，每个训练好的策略的前提都跟着变了。策略被钉在固件的信号处理和时序上，而不是被钉在仿真器本身上。

::: field 实战笔记：为板子重训，不是为台架
**规则：** 先量部署时的延迟（记录器的 `age_ms` 列，逐样本），再围着它定训练窗口。**什么时候：** 每次改运行时、频率、优先级或量化之后。**会出什么错：** 按台架延迟调出来的策略，飞在板子的延迟下。**Microduck：** Jetson 上的部署回路跑 50 Hz，归一化器烧进 ONNX，量到的总线延迟 60-120 ms，对应训练里抽 3-6 步的延迟环。我笔记里关于这条路径的内容到此为止；它的时序还没有像 ESP32 这样被拆开过。
:::

策略现在在验证过的移植上、在预算之内运行，挡在一排不信任它的门后面；而板子交回来一个延迟窗口和一个自锁。两件事都得重训。

## 常见坑

- **因为教科书这么说就去量化（第 2 拍）。** 在有浮点单元、没有向量单元的芯片上，经由解释器跑的 int16 更慢。你会看到策略间隔从 10.0 滑到 11.0 ms，p99 动作年龄从 8 涨到 13 ms。
- **用均值或玩具输入计时（第 3 拍）。** 均值随负载变，全零的 profiler 输入量到的是 `tanhf` 便宜的分支。在真实采集上取最小值。
- **把策略塞进控制节拍里（第 4 拍）。** 3 ms 中位数的推理放进 2 ms 的节拍，每个策略步都让平衡错过截止时间。把它放低一个优先级，隔着邮箱和陈旧时钟。
- **只在安静尾段或很短的校准窗口上给量化打分（第 5 拍）。** 尾段上的 1.16e-3，在关键处是 0.87；10 s 的校准截断了 4.8% 的行，代价最多 7 V。整段评分，越界行必须为零。
- **相信影子（第 6 拍）。** 在跑但不驱动的策略，看到的观测和接手时不一样。70 mm 的影子读数约 1 V，接手第一拍就打满。

## 下一步

你可能会问：策略既然已经跑起来了，这一切到底图什么？第一次刷机表明，策略自己的回灌能把它锁死；板子则表明，它的延迟窗口是在台架上定的。修这些不是打个固件补丁的事：要用新的延迟范围重训，在新对象上重跑消融，每个检查点都重新过关，然后才让机器人见到它。在一台机器人上，这个回路从头到尾是什么样子？这就是[第 18 天](../day18/)。
